# CartWise v9.7 — Test Plan (includes v9.6 and the cleanup)

**Flow:** automated tests → staging deploy → manual checks → Ben approves → production deploy. After deploying, run the history audit (section 5).

## What changed

**v9.6: Data accuracy and ops**

| Fix | Before | After |
|---|---|---|
| Ad week | The week was taken from the first deal's date, in formats Publix no longer sends. That deal was often a price drop with a "1/1" placeholder, so it fell back to "this Monday". A manual scrape on Monday or Tuesday filed last week's ad under the new week. | Uses the most common real "M/D" date among weekly-ad deals, with year rollover handled. |
| ↻ Refresh | Re-showed the browser's 5-minute cached copy. | Bypasses the browser cache and recomputes matches. |
| Schedule copy | "Every Wednesday at 8:00 AM ET", wrong from November to March. | Shown in your own time zone: "about 8:00 AM EDT" in summer, "7:00 AM EST" in winter. |
| Admin retention note | Said logs keep for 1 year. | Lists the real values: app logs 30 days, auth logs 90 days, scrape logs 1 year, history 52 weeks, cache 10 days, sessions 72 h. |
| `deploy.sh` message | Printed "20 rps, burst 50". | Prints "100 rps, burst 200", which is what it sets. |
| 2026-03-30 snapshot | 3,257 deals, about 2× a normal week. | New `tools/history_audit.py` to inspect it and fix it (section 5). |

**v9.7: Inbound list import**

| Fix | Detail |
|---|---|
| 403 when fetching the email | The endpoint is correct. Resend's **sending-access** keys "can only send emails", and Cartwise only had one. The import now uses `RESEND_RECEIVING_KEY`, a **full-access** key read from SSM `/publix/resend-receiving-key`, and falls back to the sending key. A 403 now logs exactly what to do. |
| `added_items` log | Logged the first N items parsed, not the ones actually added. |
| Unknown sender | Was dropped silently. Now logs "User not found" in Admin → Email Import. |
| Admin labels | Added for "Subject not recognized", "Rate limited" and "Rate-limit error". These rows now group under their email. |

**Cleanup**
- Removed 49 dead CSS rules: old badges, match cards, the old sensitivity bar, a duplicate toggle-switch block, and unused tag colors.
- Removed the hidden "matches loading" element, the old guessing price-display code (replaced by a tiny fallback; the API always sends `offer` now), and the `renderTpr` leftover.
- `tests/test_deal_parser.py`: removed the 4 duplicate test classes that silently replaced the newer ones, so the newer ones now run.
- `GET /user/matches` is **kept**, as the server-side "what would this week's email contain" check, and now reports the threshold it actually used.
- Copy:
  - Welcome tour and feature list: alerts go to your sign-in email; you no longer "set your notification email".
  - Panel title "Store Settings" → "My Store", matching the nav.
- Design doc: `cartwise-design-document-v9.7.md` replaces v9.1. It covers history keys, cache generations, the offer model, email, environments and the release process.

## 4. Optional: turning on inbound import

This adds a second Resend key used only to read forwarded emails. It doesn't change or rotate your existing keys.

1. In Resend → API Keys, create a key with **Full access**. Name it something like `cartwise-inbound-read`.
2. Store it in SSM:
   ```bash
   aws ssm put-parameter --name /publix/resend-receiving-key --type SecureString --value 're_FULL_ACCESS_KEY'
   ```
3. Redeploy staging (then production), and run T6.

## 5. History audit (run after the production deploy)

```bash
cd /c/Projects/Cartwise/production
python tools/history_audit.py --store 1546                         # one line per week; outliers flagged
python tools/history_audit.py --store 1546 --week 2026-03-30       # detail: row count, unique deals, duplicate ids, saving types
```

**First, check for a 2026-10-12 week.** If any manual run or "Resend This Week's Deals" happened in production since Wednesday, the old code filed the 10/7 ad under 2026-10-12. That turns every current deal into a "Repeat deal" until Wednesday. If it's there and Wednesday hasn't run yet: `python tools/history_audit.py --store 1546 --week 2026-10-12 --delete --yes`.

**What to do with the 2026-03-30 week:**
- **About 2× rows with many duplicate ids** (most likely; staging wrote the week twice): `--dedupe` (dry run), then `--dedupe --yes`.
- **No duplicates, just a big week:** leave it.
- **Clearly bad data** (for example, the wrong store): `--delete --yes`.

Every write saves a JSON backup in the current folder first, and clears the history summary so it rebuilds. Paste me the overview output if you'd like a second opinion first.
